# LogSentinel public showcase and release design

## Purpose

Ship LogSentinel as an honest, portfolio-quality public project. The public experience must make the anomaly-detection workflow understandable in under two minutes, offer an interactive browser demonstration, link to the fuller Streamlit lab when it is actually deployed, and let a developer install the research prototype without downloading private logs or large base-model weights.

## Product boundary

This release has three deliberately separate surfaces:

1. **Public showcase (Vercel).** A static, responsive site with the project story, architecture, verified capability ledger, benchmark provenance, and a self-contained sample replay. It never accepts or transmits raw customer logs.
2. **Interactive sample replay (inside the showcase).** A deterministic, clearly labelled illustrative fixture. It lets visitors select HDFS, BGL, or a synthetic security scenario and see redaction, template extraction, individual signal scores, fusion, and an alert explanation. It is not presented as a hosted production model.
3. **Research lab (Streamlit).** The existing local/full experience for working with packaged artifacts and demo fixtures. The Vercel site displays a “Launch research lab” link only when a real separately hosted URL is configured; otherwise it explains how to run the lab locally.

The Vercel deployment is a project showcase, not a claim that Vercel serves Qwen weights, trains adapters, or processes enterprise telemetry.

## Truth and provenance contract

Every visible result must have one of these states:

- **Measured:** generated by a versioned artifact and reproducible command, with dataset, split, seed, and evaluation-unit metadata.
- **Illustrative:** deterministic public sample used to explain the interface; no performance claim is attached.
- **Unavailable:** no result is shown other than the reason and command required to create it.

The showcase must not state unverified latency, cost savings, dataset metrics, “live model,” MITRE attribution, zero-day detection, or benchmark wins. Public data is described as HDFS/BGL benchmark demonstrations, not data from named companies. A future security-data profile remains clearly synthetic until backed by a published dataset and an artifact manifest.

## Information architecture

The Vercel home page uses this flow:

1. **Hero:** one-sentence purpose, local-first/privacy boundary, provenance badge, and two actions: “Explore sample replay” and “View source.”
2. **How it works:** Redact → group/time-window → score signals → calibrate and explain. Each step has one concise input/output example.
3. **Interactive replay:** environment selector, event timeline, selected-event drawer, expected-versus-observed template, component contribution chart, and an explanation generated only from the fixture fields.
4. **Evidence:** dataset/split/evaluation cards. Metrics appear only from an included generated manifest. Without a manifest, display “artifact not included in static release.”
5. **Enterprise onboarding:** a four-step isolation diagram: per-environment redaction/parser → normal-log collection → adapter/calibration package → monitored deployment/rollback.
6. **Run it yourself:** copyable local commands, package contents, checksum/signature instructions, and a disabled-by-default or configured research-lab link.

Visual language: near-black/navy shell, warm off-white content surfaces, high-contrast typography, one blue interactive accent, green/amber/red status tones paired with text/icons, generous whitespace, and no gradients or decorative clutter. Use a humanist system sans stack and numeric tabular figures. All text must meet WCAG AA contrast; the UI must work at 390 px and 1440 px widths.

## Implementation boundary

Create a small static showcase application in a dedicated `showcase/` directory. Plain HTML, CSS, and JavaScript are preferred so Vercel has no runtime dependency and the public demo stays inspectable. Use local JSON fixtures containing only redacted/sample data. Add `vercel.json` only if routing/output configuration is required.

The existing Streamlit UI receives focused corrective work rather than a broad rewrite:

- replace global colour rules that override hero/body text with scoped component classes;
- make every demo/live/illustrative state explicit;
- remove or downgrade claims without a manifest;
- make displayed API example fields match the actual API contract;
- preserve existing navigation and test seams.

The public page may link to the Streamlit app but must not iframe an unavailable local URL.

## Packaging and repository policy

Publish source, tests, documentation, small redacted fixtures, manifests, and a lightweight wheel/source distribution. Exclude `.streamlit/secrets.toml`, raw/private datasets, caches, user documents, checkpoints, external-SSD model caches, and base-model weights. The release notes explain that adapters and generated artifacts are environment-specific and should be downloaded separately only after their licensing and provenance are established.

The GitHub repository is public only after a secret scan and an explicit allowlist of staged files. The README will distinguish the static demo, local Streamlit lab, artifact generation, and optional QLoRA training. The model card and dataset card must use the same provenance language as the website.

## Deployment

Deploy only `showcase/` to Vercel. Configure the repository integration or CLI project after verifying that the production build is static and contains no secrets. Set an optional `LIVE_LAB_URL` during build only when the user supplies a real public lab deployment. Otherwise show local-run guidance. Vercel environment settings contain no credentials needed by the static site.

The release is accepted only when the production URL, GitHub README, downloadable package, and local commands agree with the actual artifacts committed to the repository. Rollback consists of redeploying the previous static deployment and reverting the release commit; no model or user data is stored on Vercel.

## Verification

Before publication:

1. Run the existing unit tests and linter; record actual counts instead of reusing prior claims.
2. Test the Streamlit/API contract with the real request and response schemas.
3. Perform a repository secret and generated-file audit, with special checks that `.streamlit/secrets.toml` and unrelated documents are untracked/ignored.
4. Render the static site and Streamlit app; inspect desktop and mobile screenshots for clipped text, contrast, hierarchy, focus visibility, and empty/error states.
5. Build the wheel and static deployment from a clean checkout; verify the package excludes raw data, secrets, and weights.
6. Verify the deployed Vercel URL and GitHub repository after publication, including all links and a hard-refresh test.

## Non-goals for this release

- No production SIEM integration, multi-tenant ingestion, cloud log upload, automatic incident response, or hosted Qwen inference.
- No benchmark-performance claim without a committed reproducible result manifest.
- No public release of enterprise/private logs or prompts derived from them.
